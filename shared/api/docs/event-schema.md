# Event Schema Reference

The [`Event`](../event.go) struct in this module is the canonical event
envelope for the Ainsel platform: connectors produce it, the hub consumes and
routes it. The platform-wide schema — including routing, trigger matching,
and connector headers — is documented in the canonical
[docs/event-schema.md](../../../docs/event-schema.md); this page is the
module-local reference for the Go types.

## Event Structure

Every event in the platform uses this format, regardless of the source
connector. The envelope carries the raw webhook delivery verbatim; payload
shape is intentionally unmodelled — there are no Go payload types.

```json
{
  "id": "evt_c-0c4b01e3_1718934000000123456",
  "version": "1",
  "connector": "c-0c4b01e3",
  "timestamp": "2026-04-24T10:30:00Z",
  "headers": {
    "X-Forgejo-Event": "issues",
    "content-type": "application/json"
  },
  "data": { "action": "opened", "issue": { "number": 42 } },
  "raw": "{\"action\":\"opened\",...}"
}
```

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique event identifier (generated by the connector) |
| `version` | string | Schema version (currently `"1"`) |
| `connector` | string | Connector **id** — the `c-…` id returned at registration, which is also the CR name. The display name never routes anything. |
| `timestamp` | time.Time | When the connector received the webhook (UTC) |
| `headers` | map[string]string | HTTP headers from the webhook delivery |
| `data` | RawJSON | Raw webhook body as parsed JSON |
| `raw` | string | Original raw webhook body as a string |

The envelope deliberately has no `source`, `type`, `subject`, `actor`, or
`action` fields. All source-specific information lives in `data` and
`headers`, so new connector types need no schema changes.

## Event Type Derivation

The event type is not part of the envelope. The hub derives a canonical type
from the webhook headers at match time: any header ending in `-Event`
(`X-Forgejo-Event`, `X-Gitea-Event`, `X-GitHub-Event`, `X-GitLab-Event`, …),
falling back to a generic `type` header. Triggers can match on it via the
synthetic `type` key in the filter payload (see Filter Examples below).

## Hub-Published Pseudo-Sources

Besides webhook connectors, the hub publishes two event kinds itself:
scheduled cron ticks and chat messages. They are labelled with the
`SourceCron` (`"cron"`) and `SourceChat` (`"chat"`) constants, and
`IsDirectSource` reports whether a connector label is one of them. These are
**not** connectors: no `WebhookConnector` CR carries either name and no
connector channel is provisioned for them — a scheduled tick or a chat
message is born directly in the target agent's channel.

## Common Payload Shapes

The shapes below are what webhook providers emit in `data` and what filters
match against. They are conventions, not Go types.

### Issue events (`X-Forgejo-Event: issues`)

```json
{
  "action": "opened",
  "issue": {
    "number": 42,
    "title": "Bug in login page",
    "body": "Steps to reproduce...",
    "state": "open",
    "labels": ["bug", "priority:high"],
    "assignees": ["alice"]
  }
}
```

### Pull request events (`X-Forgejo-Event: pull_request`)

```json
{
  "action": "opened",
  "pull_request": {
    "number": 15,
    "title": "Fix login bug",
    "body": "Fixes #42",
    "state": "open",
    "merged": false,
    "head": "fix/login-bug",
    "base": "main"
  }
}
```

### Comment events

Comments arrive as `issue_comment` / `pull_request` events with an
`action` of `created` and a `comment` object alongside the parent object:

```json
{
  "action": "created",
  "issue": { "number": 42 },
  "comment": {
    "id": 101,
    "body": "Looks good to me!",
    "created_at": "2026-04-24T10:00:00Z"
  }
}
```

### Push events (`X-Forgejo-Event: push`)

```json
{
  "ref": "refs/heads/main",
  "before": "abc123",
  "after": "def456",
  "commits": [
    {
      "id": "def456",
      "message": "fix: resolve login issue",
      "author": "alice"
    }
  ]
}
```

## Filter Examples

The hub's trigger index builds a filter payload by merging the `data` body
(fields at the top level) with the `headers` map (nested under `headers`) and
the derived `type`. Filters from `Filter`/`MatchFilters` operate on dotted
paths into that payload:

```yaml
# Match events of a given derived type
filters:
  - field: "type"
    op: eq
    value: "issues"

# Match issues with "bug" label
filters:
  - field: "issue.labels"
    op: contains
    value: "bug"

# Match PRs targeting main branch
filters:
  - field: "pull_request.base"
    op: eq
    value: "main"

# Match comments containing "/review"
filters:
  - field: "comment.body"
    op: contains
    value: "/review"
```
